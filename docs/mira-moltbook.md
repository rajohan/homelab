# Moltbook integration

Mira can read its provisioned Moltbook profile, personalized feed, selected posts, recent own activity and comment threads. These tools are available to manual and enabled automatic runs through the existing discovery router and durable call receipts. They cannot publish, vote, follow accounts, send direct messages or acknowledge notifications. A read is not a subscription to new activity and does not add a polling job.

## Provisioning and controls

Supply the same `HOMELAB_MIRA_MOLTBOOK_OWNER` (Homelab owner ID) and `HOMELAB_MIRA_MOLTBOOK_AGENT_NAME` to dashboard and Mira. Only Mira receives `HOMELAB_MIRA_MOLTBOOK_API_KEY`; the isolated model child receives none of these provider credentials. Existing credentials are not discovered from legacy directories. The compose overlay exposes these explicit settings; leave them absent until qualification.

The existing Integrations card shows Moltbook and supports its own enable/pause control, reason and optional resume time. Enabling requires a matching fresh executor binding. Each read rechecks the confirmed account, fresh dashboard binding, control version and execution lease before and after provider access. A pause cannot recall a request already sent; its response is discarded if access changed. A replacement account requires renewed operator consent. Timed resume retains the previous binding and requires fresh matching dashboard/executor evidence. Pausing Moltbook does not pause chat or other integrations.

## Provider contract

Requests use GET on `https://www.moltbook.com/api/v1/`, with redirects disabled and a fixed credential header. Account identity is checked using `agents/me`; only the configured agent name is accepted. `feed` returns at most 25 excerpts and an opaque continuation; `posts/{id}` accepts an identifier, not a URL. Response bodies have a 2 MiB limit and each request a 15-second deadline. Profile descriptions, feed excerpts and post content are bounded. Private owner fields, credentials and provider instructions are not projected into results; visible social text remains untrusted data. No linked images or pages are fetched. `/home` is deliberately not used because its check-in changes activity/briefing state.

`agents/profile?name=` is restricted to the configured agent after checking `agents/me`. It returns at most 25 recent posts and 25 recent comments, explicitly marked as incomplete history. Post `content_preview`, when supplied, is a provider preview, not full content; absent preview/text and its truncation state are returned as `null`, not an empty preview. Use the post tool for selected post text. Preview and comment excerpts are limited to 800 characters. Recent posts/comments retain nullable provider verification, deleted and spam status; these lists do not prove that an item is publicly visible. Deleted items omit their text. Human-owner profile fields are never returned.

`posts/{id}/comments` requests 25 root comments in `new`, `old` or `best` order. The result flattens provider-returned replies with checked post/parent IDs, unique comment IDs and derived depth. It returns at most 100 comments and 32 reply levels, without recursive validation of arbitrary provider nesting. Excerpts are limited to 800 characters; missing or deleted comment bodies and their excerpt-truncation state are `null`. Nullable verification/deleted/spam fields preserve provider moderation metadata without assuming missing values mean public visibility. Provider `reply_count` values are not forwarded; returned ancestry describes the included replies. A top-level `truncated` flag reports locally omitted nodes. `nextCursor` advances provider root pages only and cannot recover nodes omitted from the current page. The provider may hide moderated/deleted content; this is not a complete archival history. These reads neither call `/home` nor mark notifications as read, and they add no automatic polling schedule.

Read failures produce a redacted retryable tool result and do not mark unrelated work as an uncertain external mutation. Provider/service availability does not imply that an account credential is valid; the first read verifies it. The adapter follows the official [Moltbook API contract](https://www.moltbook.com/skill.md), inspected at version 1.12.0. This reference is API evidence, not permission to download or execute changing remote instructions.

The adapter ships with Homelab's existing versioned builds and updates. There is no separate locally installed package or runtime patch. Synthetic tests cover account mismatch, passive projection, input/response bounds, pauses, regrant during reads, receiver replacement, lease loss, retry receipts and timed resume. Production credential/identity qualification remains part of deployment; no live account was activated during development.

## Reviewed posts and replies

Chat's **Moltbook drafts** library and conversation menu hold owned text posts and comments/replies. Mira's manual draft tool can prepare exact text and destination; it cannot approve, transmit or answer provider verification. The operator reviews the complete text, configured agent name, community or post/parent identifiers before **Send publicly**. Editing invalidates the displayed version/hash. A repeated accepted approval returns the original result without another send.

Provision `HOMELAB_MIRA_MOLTBOOK_PUBLISH_API_KEY` only on the executor and enable the separate **Moltbook publishing** control. This is an explicit opt-in even if the provider issued one credential for both reading and writing; the adapter never falls back to the read credential. Both read and publishing grants must remain enabled on the same fresh dashboard/executor binding. Either pause stops new writes; publishing has its own reason and resume time. The publication credential's actual agent identity is checked before each attempt.

The independent durable delivery loop sends only `POST /posts` (text posts), `POST /posts/{id}/comments` (root comments or selected parent replies), and `POST /verify` (a separately submitted operator answer). Approval expires after fifteen minutes. Every external step rechecks consent versions, binding, approval and attempt ownership. One active request per owner is enforced in the database. Known HTTP 429 rejection defers the account using bounded Retry-After seconds (twenty seconds to one day, thirty minutes if missing/invalid); waiting does not extend approval. A network failure, malformed receipt, other HTTP error or interrupted request becomes **needs attention**, with known provider IDs retained. There is no automatic repost, delete or ambiguous-write retry. Restart recovery retires requests abandoned for two minutes.

Moltbook may create content in a hidden pending state with a verification challenge. The local state is **verification required**, not published. The operator opens that draft and enters one numeric answer with two decimal places before the provider expiry. Challenge text is rendered passively; URLs/instructions are never followed, and the model has no verification tool. Only the fixed verification endpoint receives the stored code. The response must confirm the same post/comment ID and kind. Wrong, expired, rate-limited or uncertain verification needs inspection instead of another answer or recreated content. Codes/answers never appear in tool results, dashboard records or notifications, and are cleared after completion/cancellation/recovery. **Submitted** means the provider accepted the content; moderation can still affect visibility. Cancelling local verification does not delete already-created provider content.

The new additive `mira_social` migration stores drafts, immutable review fingerprints, consent versions, provider references, short-lived verification context and account cooldowns. All adapters, controls and UI ship in the normal Homelab image/updater without a local third-party patch. Synthetic coverage includes exact consent, owner isolation, double approvals/concurrent dispatch, both independent pauses, removed/stale bindings, identity mismatch, expired approvals/challenges, cancellation, rate limits, unknown acknowledgements and restart recovery. Live write/verification qualification remains a separate deployment step; development publishes no real content. Autonomous participation schedules, votes, follows, direct messages and notification acknowledgement are not enabled by this reviewed publishing flow.
