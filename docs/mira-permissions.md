# Chat permissions

Chat settings stores a permission mode per conversation on the server. Web and Windows use the same setting, contracts, tools and queues. Existing and new conversations default to **Ask for approval**; changing model or provider preserves the mode. Task work in a linked conversation uses that conversation's setting.

| Mode             | Task changes                   | Code jobs                                        | Tested GitHub draft PRs        | Email and other publication                           |
| ---------------- | ------------------------------ | ------------------------------------------------ | ------------------------------ | ----------------------------------------------------- |
| Ask for approval | Review exact proposals in Chat | Approve each saved job                           | Approve each saved draft       | Approve each saved draft                              |
| Approve for me   | Apply requested task changes   | Run fixed Homelab source, edit and test profiles | Publish the exact tested draft | Separate approval required                            |
| Full access      | Apply requested task changes   | Run jobs allowed by the selected target          | Publish the exact tested draft | Execute requested drafts through enabled integrations |

Main code jobs accept fixed Homelab profiles only. Daytona also accepts arbitrary sandbox commands under Full access. Code jobs retain the selected target's admission limits, idle cleanup and existing resource limits. Daytona consumes subscription credits. GitHub publication creates a tested draft PR using the configured Mira identity. Separate, operator-provisioned [host administration](mira-operations.md) can run SSH, managed GitHub and deployment commands during manual work, independently of the code-test target. Full access permits requested host commands. Ask saves the exact command for human approval with fresh operator verification. Approve for me sends the command and bounded current human conversation context to an independent, tool-free reviewer on the selected provider. Only an explicit approve verdict permits execution; uncertainty, refusal or reviewer failure leaves a durable human request. The reviewer cannot expand host access, sandbox scope or integration grants. Existing review, merge and deployment requirements still apply.

Permissions cover requested work, not unrelated activity. Integration enablement, pauses, owner bindings, input-file checks and provider qualification still apply. For public websites in manual Chat, Ask requires a session grant, Approve for me allows reading and navigation, and Full access also allows clicking and typing. The browser switch, stop control, and five-minute limit apply in every mode. Saved sign-ins, file transfers and PC access require separate operator choices. Automatic runs use their existing explicit grants; Chat modes do not broaden automations or unpause dashboard improvement. Automatic memory maintenance remains governed by the separate memory/history controls.

## Execution and revocation

New actions use the conversation's current server-owned permission mode, including changes made during an active run. Task tools either create reviewable proposals or apply changes transactionally. `mira_action_execute` accepts a saved draft's kind, ID, version and content hash; the server reads its actual content and requires the same owned conversation. The existing approval functions record the model actor and origin run, then enqueue work. The model never receives a provider credential or impersonates a human approval.

Queued is not completed. Existing outboxes and job workers record outcomes, verify authority before external writes and retain uncertain attempts for inspection instead of repeating them. The origin run may finish successfully before its queued action completes. Cancellation, an interrupted/failed origin, an expired live lease, task stop, archive/deletion or changed permission invalidates delegated authority. Changing permission away and back, or archiving and restoring, does not revive earlier approvals. Direct human approvals and automation grants retain their existing independent rules.

Chat settings remain available during work. Saving a different permission mode permanently revokes earlier delegated approvals in that conversation. New actions in the same active run may use the new mode without ending the reply. Every change advances the revocation boundary; changing away and back never revives old approvals. Existing integration pause and job cancellation controls remain available. Revocation prevents later work; it cannot undo an external operation that has already been accepted.

## Deployment

The additive migration adds nullable `approval_run_id` references to the five existing action queues and `approval_revoked_at` to runs. Existing rows retain their human/policy approval path; no existing conversation receives broader permissions. Deploy dashboard, Mira and the Main code worker together before offering these modes: older workers do not implement delegated revocation. Do not roll workers back while delegated actions are queued or running; pause/cancel and reconcile those actions first. The migration does not move credentials, change provider grants or activate automations.

Regression coverage uses a disposable PostgreSQL database and fake provider transports: all modes, same-owner/conversation checks, exact versions, stale leases, duplicate tool calls, Main/Daytona classification, queued email delivery, revocation and explicit human approval. Shared component tests cover defaults, all options, disabled controls and preservation of provider/context/target settings.

## Requests in Chat

Web and Windows share compact requests immediately above the composer. Approval needed opens the shared review dialog with exact fields and approval/rejection actions. Questions can be minimized and reopened without losing drafts. Previous/next request controls appear only when there are multiple requests; previous-question navigation appears only when there is an earlier question. Selecting an option immediately advances or submits; free text uses the right-aligned Send/Next action. No default or silence submits an answer. Question text is saved as an assistant message, separately from the operator's answer. Pending requests remain available when a reply ends or the client reconnects, for up to 24 hours. Stopped, archived or deleted work cannot be resumed by an old card. A permission change invalidates old action approvals while unanswered questions remain available.

Host approvals bind the owner, conversation, exact normalized command hash and host connection fingerprint. A human decision is saved atomically with a normal chat continuation. The resumed tool consumes that saved approval once and records the actual execution separately. A consumed or uncertain attempt cannot be replayed. Questions use the same durable request storage and conversation queue; exact-hash checks and idempotent answers prevent duplicate continuations. Answers supply operator context, never action permission.

This follows the documented [permission modes](https://learn.chatgpt.com/docs/permission-modes) and [automatic review](https://learn.chatgpt.com/docs/sandboxing/auto-review.md) interaction: asking the operator, independent automatic review and broader access are separate decisions. Homelab retains its own integration grants, fresh human verification, branch protection and release requirements. These cards do not replace browser or local PC consent.

Deploy dashboard and Mira together. No schema migration is needed; pending requests use existing durable tool receipts. Regression tests use disposable data and fake host transports, including completion/reconnect, free text, exact-hash conflicts, duplicate replies, reviewer decisions and permission revocation.
