# Automatic frontend improvements

An improvement automation can submit one small frontend change through an explicit, per-automation coding permission. The durable server workflow verifies the current source and competing PRs, queues the fixed check on the selected Main or Daytona target, waits for successful results and confirmed sandbox deletion, then queues one draft PR with Mira. The model turn can finish, fail or lose its lease while these accepted steps continue. Explicit cancellation still revokes the workflow. Outcome reports link back to the originating run and the recorded jobs. Durable completion publishes one private dashboard notification in the same transaction, independently of the model-turn notification. Silent delivery, intentional pauses, revoked permission and cancellation remain quiet.

This implements the workflow, not production activation. A qualified Main host or Daytona account/snapshot, plus dedicated Mira GitHub credentials, remain deployment prerequisites. Existing automations receive no coding permission automatically.

## Operator workflow

In **Automations**, open the improvement automation's actions and choose **Code permissions**. Choose **Code execution** in the automation settings, then review the scope and resource use before allowing it. Both qualified integrations must be enabled and current. The schedule and **Automatic work** control remain independent; allowing code changes does not enable either or start a run. Permission applies only to runs created after the grant.

The fixed policy allows at most ten `.ts`, `.tsx` or `.css` files beneath `apps/dashboard/src/browser/` and `packages/ui/src/components/`. Each original and replacement is limited to 64 KiB, with a 256 KiB complete edit-plan limit. Existing files require exact original SHA-256 fingerprints; the plan is bound to current main. There is one fixed ten-minute check per submitted run, at most two accepted attempts per rolling 24 hours, and one globally active or unresolved automatic workflow. Failed preflight attempts count. Main and Daytona share the existing code-job queue and capacity controls. Daytona retains its separate cloud admission limits. These limits bound work; they are **not a currency cap**. The dialog identifies Daytona credits/billing or Main CPU/RAM before permission is granted. Main runs the same fixed check in an isolated 4 CPU / 8 GiB container without production mounts or credentials; it needs no Daytona account.

The automation inspects tasks, current source, applicable repository instructions and open PRs using passive tools, then calls `mira_improvement_submit`. Submission only means queued. A changed main, incomplete inventory, existing open Mira PR, invalid source, failed check or unconfirmed cleanup prevents publication. PR listings are observations and cannot atomically exclude a competing PR opened after the final check. GitHub publication uses the existing exact-content outbox, fixed repository/account, verified author and committer, and uncertain-write protections. The workflow never merges or deploys.

Improvement runs have a restricted tool surface for repository, task and operational context. Private memory, inbox and unrelated integration tools are denied. The automation kind is captured when the run is queued; later definition edits cannot widen that run's tool access. Legacy automatic runs without a captured kind receive the restricted surface. No GitHub or Daytona credential is passed to the model or sandbox. Repository content cannot grant new authority or change the fixed command. Other automation kinds and ordinary Chat cannot submit an automatic improvement.

## Untrusted code and CI

A model-generated draft is untrusted executable code, including tests and browser modules imported by tests. The automatic policy cannot edit workflows or expand its frontend path allowlist. Repository PR checks therefore execute in a reusable workflow with no passed or inherited secrets and only a read-only repository token. The parent preserves the required `verify` check with a result-only gate that fails if those checks fail, skip or are cancelled. Codecov uploads run on a separate fresh runner after verification, using the protected base for Git metadata and configuration. The report is downloaded outside that checkout, accepted only as one bounded regular UTF-8 file and copied to a separate destination. The uploader disables plugins, report discovery and source-file fixes; no artifact or PR source is executed there. Coverage metadata explicitly identifies the tested PR head. Container publication remains release-only on a separate runner, and CodeQL uses static extraction without a build.

Keep this CI boundary when adding automation or new credentials: draft status and a successful sandbox test do not make generated code trusted. Human review and branch protection still control merge and release. See [GitHub's untrusted-code guidance](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/).

## Pause, changes and recovery

Pause the individual automation, Automatic work, the selected execution target or GitHub to revoke the workflow's captured control versions. Re-enabling does not revive old work. Revoking the coding permission, editing the automation, changing its execution target or mapped host/account/snapshot, cancellation, deleted conversation or a one-hour workflow lifetime also stop further steps. Definition/provider changes need a fresh coding grant. The run captures its target at enqueue; missing or changed configuration never falls back to the other target. Existing Daytona permissions retain their original scope. The legacy `daytona_control` database column stores the selected execution control version for both targets. Whole-sandbox cleanup continues independently of permission, and an already-issued external request may still finish.

The coordinator and outboxes hold separate durable leases. Restarting the executor resumes recorded local phases without starting a second provider mutation. A failed check is not automatically retried. An uncertain publication remains blocked and is never resent. Review **Code jobs** and **Code changes** on Jobs. Confirm or resolve sandbox cleanup first; an uncertain GitHub result needs a successful **Inspect GitHub** observation within fifteen minutes. Then the automation's Code permissions dialog accepts a review note and **Close reviewed attempt**. This records the operator decision and releases the automatic-work block; it does not change the external outcome, erase the proposal or retry a write. Existing open Mira PRs still block the next attempt.

Queued and active attempts protect their conversations and input files from deletion. Active and unresolved attempts also prevent automation deletion or type changes and conversation deletion, keeping the operator recovery dialog reachable. The generated edit file stays protected across coordinator phases and while an outcome needs review. After completion, conversation deletion scrubs the retained edit payload and message while preserving bounded operational identifiers. The migration adds grants and attempts without granting or enabling any existing automation.

## Validation

Synthetic provider integration tests exercise grant ownership/versioning, old-run rejection, concurrency and daily admission, private-tool denial, source preflight, pause during reads, check/cleanup failures, modified artifacts, downstream revocation, publication and report creation, deletion protection and reviewed recovery. UI tests cover exact-version consent, unavailable-provider revocation and review-note submission. Main tests also exercise the durable host dispatcher, edit transfer, result collection, active revocation and cleanup with a synthetic container boundary. No live provider writes or paid sandbox allocations are needed for these tests.
