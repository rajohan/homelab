# Daytona adapter qualification

The first Daytona delivery adds the control-plane adapter only. It is not registered in the executor, scheduler, chat tools or dashboard routes, and it creates no resources at startup. Durable admission, execution, logs, artifacts, cancellation UI and production activation follow in a separate reviewed change. This document is not a claim that the full Daytona integration is deployed.

## Version and transport

Mira pins the official `@daytona/api-client` at `0.226.1` in its Bun workspace. The existing weekly Bun Dependabot group includes it; dependency changes follow the existing `chore(deps)` patch-release policy. No third-party package is patched. The generated request-parameter builders provide the current API routes and typed payloads; Homelab sends those requests using its bounded fetch transport. It does not instantiate the high-level SDK, inherit its dotenv configuration, initialize telemetry or start background sockets. Requests use the fixed `https://app.daytona.io/api` origin, reject redirects, omit cookies, cap metadata at 256 KiB and bound headers plus body delivery to 15 seconds. They are not automatically retried.

The reviewed official SDK `0.226.1` uses connection retry rules, automatic environment discovery and optional telemetry. Its explicit `otelEnabled: false` does not override an environment value of `true`. The generated client avoids importing those runtime behaviors without a local patch. See the [official clients](https://github.com/daytona/clients) and [Daytona API](https://www.daytona.io/docs/en/api/).

## Provisioning contract

The adapter parser accepts only these explicit executor settings. They are not yet wired into the service environment or deployment examples:

- `HOMELAB_MIRA_DAYTONA_TRUST_BOUNDARY`: must explicitly be `dedicated-organization`. The operator must provision an organization used only by Mira, retain its own trusted owner access and revoke keys distributed to other applications or people. This is a provisioning requirement, not a claim that API-key authentication can enumerate every key.
- `HOMELAB_MIRA_DAYTONA_NETWORK_ACCESS`: must explicitly be `provider-default`. Network access is allowed for build dependencies; no deny-all guarantee is made.
- `HOMELAB_MIRA_DAYTONA_OWNER`: Homelab owner subject.
- `HOMELAB_MIRA_DAYTONA_ORGANIZATION_ID`: exact provider organization UUID.
- `HOMELAB_MIRA_DAYTONA_SNAPSHOT_ID`: exact private snapshot UUID, not a mutable name or default image.
- `HOMELAB_MIRA_DAYTONA_TARGET`: selected provider region.
- `HOMELAB_MIRA_DAYTONA_API_KEY`: executor-only credential. It never enters the model environment or sandbox payload.

Before creation, `/api-keys/current` must confirm the configured organization, a live credential and both `write:sandboxes` and `delete:sandboxes`. Fresh organization and membership reads must confirm an unsuspended matching organization with exactly one member: the credential creator, in the owner role. Failure, missing data or another member prevents creation before the admission callback. Cleanup does not depend on these creation checks. The private snapshot must belong to that organization, be active, use the container class, and declare exactly 2 CPU, 4 GiB memory, 10 GiB disk and no GPU. An immutable, clean snapshot with Bun 1.4.4 and the qualified execution harness must be provisioned and checked before activation. Metadata alone does not prove the installed Bun version or absence of baked-in secrets. No live account or snapshot has been qualified by this change.

Create requests specify those resource limits, no volume mounts, no linked sandbox, no mounted secrets, no host environment, no KVM, private previews and `networkBlockAll: false`, with no sandbox allow list or proxy. This deliberately permits provider-default outbound networking for package installation. Tier 1/2 allow essential services; Tier 3/4 may allow the full internet. There is no inferred deny-all boundary and no tier upgrade is requested. Only explicitly approved inputs may enter this environment; host credentials, production data and unrelated files must never be exported. See [Daytona network limits](https://www.daytona.io/docs/en/network-limits/). A future strict-network mode must independently qualify the effective policy before use.

[Daytona runtime access](https://www.daytona.io/docs/en/api-keys/) is organization-wide, regardless of key resource scopes. `private` prevents public preview access; labels identify an attempt within the trusted organization and do not isolate it from other organization credentials. Runtime deployment therefore requires the dedicated-organization provisioning contract above. The owner must not share keys or add members while jobs are active. The adapter checks sole-owner membership before creation, but an API key cannot prove absence of other keys: manager-key listing only returns that manager's children. Do not introduce a false full-inventory check or grant the executor key-management privileges. Document and qualify existing owner sessions and keys before activation; pause admissions and revoke unused keys when this boundary changes.

The network choice and organization trust contract are included in the binding fingerprint. Credential rotation within the same organization preserves it.

The provider receives a 15-minute wall-clock TTL, 2-minute queue timeout request, 5-minute idle stop and immediate deletion after stop. [Daytona's lifecycle contract](https://www.daytona.io/docs/en/typescript-sdk/daytona/) distinguishes TTL from idle stop/delete; TTL applies regardless of sandbox state. Queue timeout is only honored when the organization enables its queue-timeout feature. The TTL is the independent resource bound. Provider billing and aggregate daily spending limits still require the durable queue layer and account qualification; this adapter does not claim to enforce a currency budget.

## Caller obligations and recovery

A future durable dispatcher must persist the immutable binding, a unique attempt UUID and create-attempt state before invoking the final `authorize` callback. The callback must atomically recheck owner controls, lease, approval/admission policy and concurrency/spend limits. Call `create` at most once for that attempt. The adapter performs account/snapshot preflight before this callback and immediately returns the create receipt without waiting for readiness. Persist the returned provider ID before any subsequent step.

A deterministic `mira-<binding-prefix>-<attempt-UUID>` name and full binding/attempt labels allow `inspect` to find an already created sandbox after an acknowledgement is lost. Account, name, labels and any recorded provider ID must all agree before accepting an observation or sending DELETE. A timeout, cancellation during dispatch, HTTP error or malformed mutation response produces `DaytonaUncertainMutation`; it must never return to an automatic create/replay path. Even a subsequent 404 does not prove that a timed-out creation cannot still appear. Retain unresolved attempts for reconciliation through their expected lifetime and report uncertainty rather than freeing the admission slot early.

`settingsMatch` means the observed environment is explicitly empty and the requested resource, preview, networking, region, snapshot and remaining TTL fields match. Missing or nonempty `env` fails the check, including opaque provider secret placeholders. A custom `otelEndpointOverride` also fails the check: sandbox telemetry must use the provider's default collector, with the override absent, null or empty. The endpoint is never exposed in observations. This is metadata comparison, **not execution readiness, exclusivity proof or a network containment guarantee**. Callers must also perform a fresh `preflight(signal, true)`, enforce the dedicated-organization provisioning policy, require `state === "started"`, and qualify the runtime before code execution. No execution adapter is exposed by this change. Unknown states are observations, never success. Missing or drifted settings do not block deletion of a resource whose identity remains verified. Snapshot lookup failure similarly cannot strand cleanup. Retain the original binding for cleanup after the active configuration changes.

`destroy` distinguishes an absent resource, a confirmed `destroyed` state and a merely accepted deletion request. A successful DELETE request is not completion. Poll until absence/destruction is confirmed; uncertain DELETE responses retain the known provider ID. Cleanup must remain possible while new admissions are paused, and TTL is a fallback if the executor disappears. No host command execution, SSH keys, credentials or private repository export is provided by this adapter.

## Validation

Synthetic tests exercise account, membership and snapshot disagreement, final admission revocation, cancellation before and during dispatch, uncertain writes with no replay, deterministic recovery, cross-owner/ID rejection, policy drift, cleanup during snapshot outages, explicit deletion outcomes, private response-field omission, and advertised/streamed response limits. These tests use the actual generated request builders and an injected provider transport. They incur no Daytona usage and do not replace later live qualification.
